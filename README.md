# School — منصة إدارة المدارس والمؤسسات التعليمية

منصة SaaS عربية متعددة المدارس (Multi-Tenant School ERP) بهندسة Modular Monolith باستخدام Django، مع واجهات React وتطبيق Flutter ضمن خارطة الطريق.

## حالة المشروع
المواصفات الهندسية العربية في docs/00-المواصفات-الهندسية-الشاملة.md.
خطة التنفيذ الملزمة في docs/خطة-العمل-التنفيذية.md.
تقرير المرحلة الأولى في docs/المرحلة-الأولى-تقرير-التنفيذ.md.
المشروع في مرحلة تأسيس؛ لا يعتبر جاهزاً للإنتاج قبل تثبيت الاعتماديات وإنشاء migrations وتشغيل الاختبارات ومراجعة عزل المدارس على PostgreSQL.

## المبدأ الأهم: استقلال كل مدرسة
لكل مدرسة مستخدموها وعضوياتها وأدوارها وبياناتها الأكاديمية وجداولها وطلابها ومعلموها وإشعاراتها وسجلاتها. ولكل مدرسة دفتر محاسبي مستقل ودليل حسابات وفترات مالية وصناديق وقيود وأرصدة لا تختلط مع أي مدرسة أخرى. قاعدة PostgreSQL المشتركة في البداية لا تعني اشتراك الدفاتر أو البيانات.

## التقنية
Python / Django، Django REST Framework، PostgreSQL، Django Unfold لتطوير لوحة Django Admin العربية، Redis وCelery للمهام الخلفية، React للواجهة التشغيلية، وFlutter للتطبيق الموحد.

## التشغيل
راجع دليل إعداد البيئة في docs/تشغيل-وتجهيز-البيئة.md. بصورة عامة:
```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements/dev.txt
cp .env.example .env
python manage.py check
python manage.py makemigrations
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

## قواعد التطوير
1. كل وحدة تملك نماذجها وخدماتها وواجهاتها واختباراتها.
2. التكامل عبر خدمة معلنة أو حدث موثق.
3. كل استعلام مدرسي يطبق نطاق المدرسة.
4. لا تعتمد على school_id من العميل دون التحقق من العضوية.
5. لا تحذف سجلاً مالياً أو أكاديمياً معتمداً؛ استخدم العكس أو التسوية أو الأرشفة.
6. وثق كل تغيير وأضف اختباراته وارفعه إلى GitHub في نفس دفعة العمل.
7. لا تضع الأسرار أو ملفات البيئة الحقيقية أو قواعد بيانات محلية في Git.
