# توثيق تنفيذ المرحلتين الثانية والثالثة

> نطاق هذا المستند هو ما أضيف إلى المستودع في المرحلتين الثانية والثالثة فقط. لا يتضمن بدء المرحلة الرابعة أو أي وحدات أكاديمية جديدة.

## 1. المرحلة الثانية: الهوية والمصادقة والجلسات

### تسجيل الدخول ورموز الأجهزة
- تسجيل الدخول عبر رقم الهاتف وكلمة المرور: `POST /api/v1/auth/login/`.
- يدعم رمز `Bearer` الجديد مع استمرار دعم رموز DRF القديمة بصيغتي `Token` و`Bearer` خلال فترة الانتقال.
- كل جهاز يحصل على جلسة مستقلة. تحفظ قاعدة البيانات بصمة SHA-256 للرمز، ولا تحفظ الرمز الخام.
- انتهاء الجلسة الافتراضي 30 يوماً، ويمكن تغييره عبر `API_SESSION_LIFETIME_DAYS`.
- عند تسجيل الدخول مجدداً باستخدام `X-Device-ID` نفسه للحساب نفسه، تُبطل الجلسة السابقة لذلك الجهاز فقط.
- تسجيل الخروج يبطل جلسة الجهاز الحالية، وليس جلسات الأجهزة الأخرى.

### إدارة الجلسات
| المسار | الطريقة | الوظيفة |
|---|---|---|
| `/api/v1/auth/sessions/` | GET | عرض جلسات الأجهزة النشطة للحساب الحالي |
| `/api/v1/auth/sessions/refresh/` | POST | تدوير رمز الجلسة الحالية وإصدار رمز جديد |
| `/api/v1/auth/sessions/<session_id>/revoke/` | POST | إبطال جلسة جهاز واحد يملكها المستخدم |
| `/api/v1/auth/sessions/revoke-all/` | POST | إبطال جميع جلسات الأجهزة والرموز القديمة |

لا يمكن استخدام الرمز السابق بعد تدوير الجلسة. ولا يمكن إبطال جلسة تخص مستخدماً آخر.

### التسجيل والتحقق واستعادة كلمة المرور
| المسار | الطريقة | الوظيفة |
|---|---|---|
| `/api/v1/auth/register/` | POST | إنشاء حساب مبدئي غير نشط وإرسال رمز الهاتف |
| `/api/v1/auth/phone/verify/` | POST | التحقق من الرمز وتفعيل الحساب |
| `/api/v1/auth/phone/resend/` | POST | طلب رمز بديل لحساب بانتظار التفعيل |
| `/api/v1/auth/password/reset/request/` | POST | طلب رمز استعادة كلمة المرور |
| `/api/v1/auth/password/reset/confirm/` | POST | تعيين كلمة مرور جديدة وإبطال كل الجلسات السابقة |
| `/api/v1/auth/password/change/` | POST | تغيير كلمة المرور من جلسة مصادق عليها |

رمز OTP مكون من ستة أرقام، صالح لخمس دقائق، وتخزن بصمته فقط. يحدد النظام حدوداً لعدد الطلبات وفترة انتظار إعادة الإرسال، ويحفظ محاولات التحقق الفاشلة ويستهلك التحدي بعد خمس محاولات غير صحيحة. تطبق متطلبات كلمة المرور المعرفة في إعدادات Django.

### إعداد مزود الرسائل النصية

لا يتضمن المستودع اعتماداً على شركة SMS بعينها. يجب أن يُهيأ مزود الرسائل في بيئة التشغيل عبر المتغير:

```env
PHONE_OTP_DELIVERY_BACKEND=your_package.your_module.your_callable
API_SESSION_LIFETIME_DAYS=30
DEFAULT_FROM_EMAIL=no-reply@example.com
```

يجب أن يكون المسار قابلاً للاستيراد ويشير إلى دالة تستقبل الوسائط المسماة التالية:

```python
def send_sms(*, phone: str, message: str, purpose: str) -> bool:
    ...
```

تعيد الدالة `True` عند قبول المزود للرسالة، و`False` عند الفشل. إذا لم يُضبط المزود، ترفض واجهات إرسال OTP العملية ولا تصدر رمز تحقق للاستخدام. كما يجب ضبط SMTP فعلي في الإنتاج؛ إعداد البريد الافتراضي في بيئة التطوير/العينة لا يثبت تسليم بريد خارجي.

### الأمان والصلاحيات
- أضيفت جلسات قابلة للإبطال لكل جهاز مع دعم انتقالي للرموز القديمة.
- أضيف قفل مؤقت للحساب بعد خمس محاولات دخول فاشلة، لمدة 15 دقيقة.
- فُرضت حدود مستقلة على مستوى عنوان IP والهاتف؛ وتطبق حدود إضافية على مستوى الجهاز عند تسجيل الدخول. تُحوّل أرقام الهواتف ومعرفات الأجهزة إلى بصمات SHA-256 في مفاتيح التخزين المؤقت، فلا تحفظ القيم الخام في مفاتيح throttle.
- الحدود الافتراضية: الدخول 10/دقيقة لكل IP و5/دقيقة لكل هاتف و10/دقيقة لكل جهاز؛ التسجيل 3/ساعة لكل IP ولكل هاتف؛ طلب OTP 3/ساعة لكل IP ولكل هاتف؛ التحقق من OTP 8/دقيقة لكل IP و5/ساعة لكل هاتف؛ وطلب الاستعادة 3/ساعة لكل IP ولكل هاتف. ويبقى حد إصدار OTP داخل الخدمة 5/ساعة لكل حساب مع فاصل 60 ثانية.
- يستخدم التطبيق Redis عند ضبط `REDIS_URL`، وهو متغير موجود في `.env.example`، لتشارك حدود الطلبات بين عمال Gunicorn والنسخ الخادمة. في التطوير والاختبارات دون Redis تستخدم ذاكرة محلية؛ يجب إعداد Redis مشترك في الإنتاج حتى تكون الحدود موحدة بين جميع النسخ.
- عند إيقاف الحساب أو تعطيل `is_active`، تُبطل جميع جلسات الأجهزة وتحذف رموز DRF القديمة داخل معاملة واحدة. إعادة تفعيل الحساب لا تعيد صلاحية أي بيانات اعتماد سبق إبطالها.
- حُصرت صلاحيات أدوار المدرسة في التطبيقات التشغيلية المدرسية المسموح بها؛ لا يجوز لمدير مدرسة منح صلاحيات Django أو الحسابات العامة أو إدارة المستأجرين أو المنصة.
- طُبقت قائمة الصلاحيات المسموح بها في API وفي لوحة الإدارة، كما يرفض فحص الصلاحيات المركزي أية صلاحية خارج القائمة حتى لو وُجدت بيانات قديمة في دور.
- سياق المدرسة يرفض المدارس المؤرشفة، كما أن قبول الدعوة لا يعيد تفعيل عضوية موقوفة أو منتهية.

## 2. المرحلة الثالثة: ملفات الأشخاص وشؤون الطلاب

### ربط حساب الطالب وفصله
- ربط الحساب: `POST /api/v1/students/<student_id>/account/` مع رقم الهاتف.
- الفصل: `DELETE /api/v1/students/<student_id>/account/`.
- يشترط الربط حساباً نشطاً ورقم هاتف موثقاً.
- يمنع ربط الحساب بأكثر من ملف طالب نشط داخل المدرسة نفسها.
- تنشأ عضوية المدرسة ودور الطالب عند الحاجة، ويُرفض تجاوز عضوية معلقة أو موقوفة أو منتهية.
- فصل الحساب لا يحذف المستخدم ولا عضويته العامة ولا بياناته؛ يزيل ارتباط ملف الطالب ودور الطالب فقط.
- لا تعرض واجهات الطالب والأسرة بيانات الهوية الوطنية أو تاريخ الميلاد أو الرصيد المالي. تعرض البيانات المالية فقط للأدوار المالية المخولة، وتبقى تفاصيل الهوية الحساسة متاحة للأدوار الإدارية المدرسية المناسبة.

### ولي الأمر والروابط العائلية
- إنشاء ملف ولي الأمر وربطه بالحساب يتطلب حساباً نشطاً ورقم هاتف موثقاً.
- إنشاء وتعديل علاقة ولي الأمر بالطالب يتحقق من تبعية الطرفين إلى المدرسة نفسها ويضمن عضوية ولي الأمر ودوره.
- لا يحصل دور الطالب أو ولي الأمر على صلاحيات Django مباشرة؛ تعتمد الواجهات العائلية على قواعد الأدوار والارتباطات الصريحة بين الحساب والملف.

### حركات الطالب وسجل القيد
أضيف نموذج `StudentMovement` كسجل تاريخي append-only لحركات:
- القبول والتسجيل.
- النقل الداخلي بين الشعب في المدرسة والسنة نفسها.
- الترفيع وإعادة القيد للسنة التالية.
- التخرج والانسحاب.

يحفظ السجل موضع الطالب قبل الحركة وبعدها، وتاريخ سريانها، والسبب، ومن سجلها. لا يسمح بتعديل الحركة أو حذفها. تسجل عمليات الحركات كذلك في سجل التدقيق. أضيف قيد يمنع ربط حساب واحد بأكثر من ملف طالب نشط في المدرسة ذاتها؛ وتوقف migration بوضوح عند اكتشاف روابط قديمة مكررة بدلاً من اختيار ملف أو حذف بيانات تلقائياً.

يفرض نموذج `StudentEnrollment` عند الحفظ عبر ORM تطابق المدرسة للطالب والسنة والصف والشعبة، وتطابق الصف والسنة مع الشعبة؛ كما تحفظ عملية إنشاء الطالب وقيده السنوي الأول داخل معاملة واحدة.

### واجهات الطالب الإضافية
| المسار | الطريقة | الوظيفة |
|---|---|---|
| `/api/v1/students/<student_id>/transfer/` | POST | نقل داخلي إلى شعبة أخرى ضمن السنة والصف نفسيهما |
| `/api/v1/students/<student_id>/movements/` | GET | سجل حركات الطالب، للموظفين الأكاديميين المخولين |
| `/api/v1/students/import/preview/` | POST | معاينة ملف CSV والتحقق من الصفوف قبل الحفظ |
| `/api/v1/students/import/commit/` | POST | تنفيذ الاستيراد بعد التحقق الكامل |
| `/api/v1/students/export/` | GET | تصدير كشف الطلاب إلى CSV |

### الاستيراد الجماعي
- يقبل CSV بترميز UTF-8/UTF-8 BOM.
- الحد الأقصى للملف 2 ميجابايت و500 طالب في الطلب.
- يجب أن يتضمن الملف: `student_id_number`, `first_name`, `last_name`, `academic_year_id`, `grade_level_id`, `section_id`.
- الحقول الاختيارية: `middle_name`, `gender`, `enrollment_date`, `birth_date`, `national_id`.
- تتحقق المعاينة من انتماء السنة والصف والشعبة إلى المدرسة، ومن تطابق الشعبة مع الصف والسنة، ومن عدم تكرار الرقم المدرسي داخل الملف أو في سجلات المدرسة النشطة.
- لا يحفظ طلب المعاينة أي سجلات.
- عملية الالتزام ذرية: إذا وجدت أخطاء أو تعذر تخصيص السعة فلن يثبت أي سجل من الملف. تقفل الشعب أثناء التخصيص وتُنشأ حركة قبول لكل طالب مستورد.
- يصدر ملف التصدير عناوين الأعمدة والمعرفات اللازمة لإعادة الاستيراد، ويحتوي على بيانات الهوية؛ لذلك لا يسمح به إلا لدور شؤون الطلاب والإدارة المخولة.

## 3. ترحيل قاعدة البيانات والتشغيل

أضيفت migrations:
- `accounts.0003_device_sessions_phone_challenges`
- `students.0005_studentmovement_unique_account_binding`

قبل تطبيقها على بيانات الإنتاج:
1. خذ نسخة احتياطية قابلة للاستعادة من قاعدة البيانات والملفات.
2. افحص وجود أكثر من ملف طالب نشط في المدرسة نفسها مرتبط بحساب المستخدم نفسه. Migration المرحلة الثالثة تتوقف عمداً عند وجود مثل هذه الحالات؛ عالجها يدوياً بعد مراجعة الإدارة ولا تحذف أو تدمج السجلات آلياً.
3. جهز مزود SMS حقيقياً واضبط متغير البيئة `PHONE_OTP_DELIVERY_BACKEND`، وجهز SMTP قبل تفعيل التسجيل/الاستعادة والإشعارات الفعلية.
4. شغل `python manage.py migrate --plan` ثم migrations في نافذة صيانة مناسبة، وبعدها اختبر التسجيل والتحقق وتسجيل الدخول وإبطال الجلسات وربط الحسابات واستيراد CSV.
5. لا تعتبر نجاح CI بديلاً عن اختبار تسليم الرسائل أو ترحيل نسخة قاعدة بيانات الإنتاج.

## 4. حدود النطاق

هذه التغييرات لا تبدأ المرحلة الرابعة. لم يُضف إعداد أكاديمي جديد أو وحدة تدريسية مستقلة ضمن هذا العمل. بقيت عمليات الترفيع وإعادة القيد والتخرج والانسحاب ضمن واجهاتها الحالية، مع إضافة سجل الحركة والتحقق من سلامة الروابط والسعة.

## 5. استكمالات التدقيق النهائي في المرحلتين

- تغطي اختبارات المصادقة حدود الهاتف عند تبديل عناوين IP، وحدود استعادة كلمة المرور عبر عناوين IP متعددة، ومنع إحياء الجلسات القديمة عند إيقاف الحساب ثم إعادة تفعيله.
- تغطي اختبارات شؤون الطلاب تعدد أولياء الأمر للطالب الواحد، واشتراط الهاتف الموثق والعضوية السارية عند ربط ملفات المعلم والموظف.
- أضيفت اختبارات مستقلة لإعادة القيد والتخرج والانسحاب، إلى جانب النقل والترفيع والاستيراد والتصدير.
- أضيف تحقق ORM لقيد الطالب السنوي حتى لا يستطيع كود داخلي أو لوحة الإدارة إنشاء قيد لشعبة لا تتبع المدرسة أو الصف أو السنة المحددة.
