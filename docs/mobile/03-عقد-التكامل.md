# عقد تكامل تطبيق Expo مع School API

**المصدر:** apps/api/urls.py وapps/api/views.py وapps/api/v1/urls.py وapps/api/v1/views.py وapps/students/api/views.py وdocs/api/README_AR.md  
**الفرع:** feature/mobile-expo-foundation  
**تاريخ المراجعة:** 3 نوفمبر 2026

هذا المستند يربط الشاشات بالمسارات الموجودة فعلياً وفق مراجعة الشفرة والوثائق. وجود المسار لا يثبت وحده اجتيازه لاختبارات PostgreSQL أو الإنتاج.

## 1. المصادقة والحساب

### التسجيل برقم الهاتف
- POST /api/v1/auth/register/
- POST /api/v1/auth/phone/verify/
- POST /api/v1/auth/phone/resend/
- POST /api/v1/auth/password/reset/request/
- POST /api/v1/auth/password/reset/confirm/

مدخلات التسجيل تشمل phone وfirst_name وlast_name وpassword وpassword_confirm، مع middle_name وemail اختياريين. التسجيل ينشئ حساباً pending ويرسل OTP؛ تأكيد OTP يثبت الهاتف ويفعل الحساب.

**نجاح توثيق الهاتف لا ينشئ عضوية مدرسة ولا يمنح دور طالب/معلم/ولي أمر.** الربط بالمدرسة والملف الشخصي خطوة مستقلة.

### الدخول والجلسات
- POST /api/v1/auth/login/
- POST /api/v1/auth/logout/
- POST /api/v1/auth/sessions/refresh/
- GET /api/v1/auth/sessions/
- POST /api/v1/auth/sessions/{session_id}/revoke/
- POST /api/v1/auth/sessions/revoke-all/

طلب الدخول:
~~~json
{
  "phone": "+9677XXXXXXX",
  "password": "password",
  "device_id": "stable-device-id",
  "device_name": "Android phone"
}
~~~

الاستجابة الحالية تتضمن access_token وtoken_type وsession_id وdevice_id وexpires_at وuser وschools، كما يحتفظ الخادم بحقل token للتوافق القديم. التطبيق يستخدم access_token من نوع Bearer ويخزنه في Expo SecureStore ولا يحفظ كلمة المرور.

إرسال X-Device-ID واسم الجهاز مستحسن. تسجيل الخروج يبطل جلسة الجهاز الحالية عند استخدام DeviceSession. التجديد يدور الرمز ويعيد access_token جديداً.

## 2. سياق المدرسة
- GET /api/v1/schools/
- GET/PATCH /api/v1/me/
- GET /api/v1/app/account/profiles/

كل طلب محمي داخل مدرسة يرسل:
~~~http
Authorization: Bearer <access_token>
X-School-ID: <school_uuid>
Accept: application/json
~~~

المسار /api/v1/school-context/ موجه أساساً إلى جلسة Django في واجهة الويب. تطبيق الهاتف يعتمد X-School-ID في كل طلب ولا يجعل session cookie مصدر سياق المدرسة.

بعد الدخول يقرأ التطبيق المدارس الفعالة، ثم يختار المدرسة، ثم يقرأ الملفات والأدوار الخاصة بها. عند تعدد الملفات يطلب تحديد مساحة العمل. تبديل المدرسة يفصل cache المدرسة السابقة.

## 3. الدعوات والعضويات
- GET/POST /api/v1/app/account/invitations/
- POST /api/v1/app/account/invitations/accept/
- POST /api/v1/app/account/invitations/{invitation_uuid}/revoke/

إصدار الدعوة إجراء إداري؛ يقبل phone أو email وrole_ids وexpires_at اختيارياً. قبول الدعوة يتطلب حساباً مصادقاً عليه وتطابق وسيلة الاتصال الموثقة مع الدعوة. لا ينشئ التطبيق العضوية محلياً؛ ينتظر نتيجة الخادم ثم يعيد تحميل المدارس والملفات.

## 4. الطالب
- GET/POST /api/v1/students/
- GET/PATCH /api/v1/students/{student_uuid}/
- POST /api/v1/students/{student_uuid}/promote/
- POST /api/v1/students/{student_uuid}/retain/
- POST /api/v1/students/{student_uuid}/graduate/
- POST /api/v1/students/{student_uuid}/withdraw/
- POST/DELETE /api/v1/students/{student_uuid}/account/

ربط حساب هاتف بملف طالب موجود يتم عبر المسار account من جهة تملك صلاحية إدارة شؤون الطلاب. الشفرة تتحقق من أن الهاتف يخص حساباً موجوداً، ثم تنفذ خدمة الربط. لا يسمح بربط الحساب بمجرد إدخال اسم الطالب أو رقمه من شاشة عامة.

## 5. ولي الأمر والأبناء
- GET /api/v1/app/my/children/
- GET/POST /api/v1/app/guardians/
- GET/POST /api/v1/app/guardian-relations/

ولي الأمر يرى الأبناء المرتبطين بملفه داخل المدرسة النشطة. إنشاء ملف ولي الأمر وإدارة علاقته بالطالب حالياً من مسارات تتطلب أدواراً إدارية في شؤون الطلاب. لم يظهر مسار مكتمل لطلب ربط ذاتي من ولي الأمر؛ يجب ألا ننفذ ذلك قبل إضافة API آمن للتحقق والاعتماد.

## 6. المعلم
- GET/POST /api/v1/app/teachers/
- GET/POST /api/v1/app/teacher-assignments/
- GET /api/v1/app/my/timetable/?profile_type=teacher

إنشاء ملف المعلم يتطلب حساباً موثقاً وعضوية نشطة وإجراءً إدارياً مخولاً. المعلم العادي يرى ملفه وإسناداته فقط. قائمة الشعب والطلاب مصدرها الإسنادات؛ لا يعرض التطبيق جميع طلاب المدرسة.

## 7. الوحدات الأكاديمية والتشغيلية

| الوحدة | المسارات |
|---|---|
| الحضور | /api/v1/attendance/ |
| الواجبات | /api/v1/app/homework/ وhomework-submissions/ |
| التقييم والدرجات | /api/v1/app/assessment-types/ وgradebook/ وexam-submissions/ |
| الرسوم | /api/v1/fees/ |
| الموظفون والرواتب | /api/v1/staff/ و/api/v1/payroll/ |
| الإشعارات | /api/v1/notifications/ |
| المحادثات | /api/v1/app/conversations/ |

يراجع دليل API الرسمي تفاصيل كل طريقة وطلب واستجابة وصلاحية. لا تستنتج CRUD من اسم المورد وحده.

## 8. قواعد العميل
- UUID يعامل كنص.
- التواريخ ترسل وفق صيغة العقد.
- 400 يعرض أخطاء الحقول، و401 يفحص الجلسة أو يطلب تسجيل الدخول، و403 يعرض عدم توفر الصلاحية.
- retry للقراءات الآمنة فقط.
- لا تعاود إنشاء فاتورة أو سند قبض أو صرف أو عكس بعد timeout قبل الاستعلام عن النتيجة.
- تستخدم idempotency_key حيث يطلبه العقد.
- لا تضع أسرار SMS أو WhatsApp أو AI داخل حزمة التطبيق.
- لا تقبل school_id أو student_id من العميل كدليل على الحق في البيانات.

## 9. فجوات التكامل المعروفة
1. لا يوجد API جاهز لطلب ربط ذاتي من ولي الأمر بملف طالب مع تحقق واعتماد.
2. خدمة إرسال Push من الخادم ومعالجة outbox تحتاج استكمالاً؛ تسجيل رمز الجهاز لا يعني اكتمال الإرسال.
3. المحادثات REST موجودة، لكن WebSocket/Realtime لم يظهر في العقد؛ تبدأ النسخة الأولى بتحديث دوري مضبوط.
4. إدارة الملفات العامة والصور وروابط التنزيل الآمنة تحتاج عقداً موحداً.
5. إعدادات هوية المدرسة وألوانها من الخادم تحتاج School Branding API جديدة.
6. يجب مراجعة التوثيق مع الشفرة والاختبارات بعد كل مرحلة.
