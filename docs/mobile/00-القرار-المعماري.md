# القرار المعماري لتطبيق School Mobile

**التاريخ:** 3 نوفمبر 2026  
**الفرع:** feature/mobile-expo-foundation  
**القرار:** Expo + React Native + TypeScript  
**الموقع:** mobile/ داخل مستودع zydan25/school

## 1. الهدف وحدود المسؤولية
تطبيق هاتف واحد يخدم الطالب وولي الأمر والمعلم والموظف والإدارة وفق عضوية المستخدم وملفاته والمدرسة النشطة. التطبيق عميل API فقط؛ لا يملك قاعدة بيانات الأعمال ولا يعيد تنفيذ قواعد الرسوم أو الحضور أو القيد أو المحاسبة.

يظل Backend الحالي مبنياً على Django وDjango REST Framework بنمط Modular Monolith. تطبيق الهاتف مستقل في البناء والاعتماديات والنشر داخل مجلد mobile، ويستهلك API v1 الحالية.

## 2. المكدس المعتمد

| الجانب | المكتبة / التقنية | الاستخدام |
|---|---|---|
| إطار الهاتف | Expo SDK 58 + React Native 0.88 | Android وiOS |
| اللغة | TypeScript | أنواع صارمة وحدود واضحة |
| التنقل | Expo Router | مسارات قائمة على الملفات |
| مكونات الواجهة | React Native Paper | بطاقات ونماذج وأزرار وحوارات |
| الأيقونات | Lucide React Native | أيقونات خطية موحدة |
| بيانات الخادم | TanStack Query | cache وpagination وmutations |
| حالة الواجهة | Zustand | المدرسة والملف النشط وتفضيلات الواجهة |
| النماذج | React Hook Form + Zod | حالة النماذج والتحقق |
| التخزين السري | Expo SecureStore | access token ومعرفات الجلسة الحساسة |
| التخزين المحلي | Expo SQLite | يضاف عند تنفيذ offline-first المحدود |
| الخطوط | Expo Font | تحميل/تضمين الخط العربي |
| الترجمة | Expo Localization + طبقة ترجمة | اللغة والمنطقة واتجاه الواجهة |
| الإشعارات | Expo Notifications | تسجيل الجهاز واستقبال الإشعارات |
| التحديثات | EAS Update | تحديثات JavaScript والأصول المتوافقة |
| البناء | EAS Build | نسخ التطوير والاختبار والإنتاج |

لا نستخدم NativeWind وReact Native Paper كنظامي تصميم متوازيين في البداية. React Native Paper هو أساس المكونات، وتضاف مكونات School الخاصة فوقه. جميع الأيقونات من Lucide.

## 4. مسؤوليات الطبقات

- app/: مسارات Expo Router وتركيب layouts والتنقل والحماية الأولية للمسارات؛ لا يوضع فيها منطق الأعمال.
- core/: API client والمصادقة والجلسات وسياق المدرسة والتخزين السري ومزودات الحالة والتصميم والترجمة.
- shared/: مكونات UI عامة وأدوات تنسيق البيانات والتواريخ والعملات والأخطاء والنماذج.
- features/: كل وحدة تملك API functions وHooks وComponents وScreens وSchemas وTypes الخاصة بها.

## 5. إدارة الحالة
- TanStack Query هو المصدر الوحيد لبيانات الخادم وcache.
- Zustand لحالة الواجهة فقط: المدرسة النشطة والملف/الدور النشط وتفضيلات العرض.
- React Hook Form لحالة النماذج وZod للتحقق.
- لا تنسخ قوائم الطلاب أو الفواتير من TanStack Query إلى Zustand.
- مفاتيح Query تتضمن schoolId ونوع الملف ومعرفه عند تأثير ذلك على النتيجة.
- عند تبديل المدرسة أو الملف، تمنع قراءة cache من السياق السابق.
- لا تكرر الطلبات الجانبية المالية أو الاعتمادية تلقائياً بعد انقطاع الاتصال.

## 6. نظام تصميم واحد
كل شاشة تستخدم رموز theme المركزية ولا تضع ألواناً أو مسافات عشوائية. المكونات المعتمدة تشمل AppButton وAppTextField وAppSelect وAppDatePicker وAppCard وAppDialog وAppBottomSheet وAppAvatar وStudentCard وSchoolSwitcher وProfileSwitcher وLoadingState وEmptyState وErrorState.

## 7. حدود الصلاحيات
إظهار وإخفاء العناصر في التطبيق تحسين لتجربة الاستخدام وليس حماية أمنية. كل endpoint وكل سجل وكل إجراء يظل محمياً في الخادم. وجود ملف وحده لا يكفي؛ الدور يتطلب عضوية فعالة وصلاحية سارية وسياق مدرسة صالح.

## 8. المدارس والملفات المتعددة
تسلسل السياق: حساب المستخدم، ثم المدارس ذات العضوية الفعالة، ثم اختيار المدرسة، ثم الملفات والأدوار داخلها، ثم اختيار مساحة العمل، ثم تحميل بيانات تلك المساحة فقط.

## 9. الاتصال بالخادم
كل طلب محمي يرسل Authorization: Bearer والـ X-School-ID. تستخدم API v1 الحالية. عند وجود مسار قائم لا يضاف مسار ثانٍ لنفس العمل. عند غياب عقد، تسجل الفجوة ويؤجل تنفيذ الوظيفة أو ينشأ عقد خادم مع اختباره وتوثيقه أولاً.

## 10. العمل دون اتصال
لا نطبق مزامنة عامة مبكراً. المرحلة الأولى تعرض بيانات قراءة محدودة مخزنة مؤقتاً. لا يتم تنفيذ تحصيل أو عكس سند أو نشر نتيجة أو اعتماد حضور دون قبول الخادم. أي قائمة انتظار لاحقة تتطلب idempotency والتعارضات والاختبارات.

## 11. التحديث والنشر
قنوات EAS منفصلة: development وpreview وproduction. لا يرسل OTA إلا إلى Runtime متوافق مع التطبيق المثبت. أي مكتبة Native أو صلاحية أو إعداد Native جديد يحتاج إصدار متجر جديد. لم يتم ربط Project ID أو حساب EAS في هذا التأسيس.

## 12. معيار قبول أي وحدة
- حدود الملفات والمسؤوليات واضحة.
- جميع طلبات API في مجلد api الخاص بالميزة.
- المكونات قابلة لإعادة الاستخدام.
- أنواع API ونماذج Zod متطابقة مع العقد.
- المدرسة والملف يدخلان في نطاق الاستعلامات.
- حالات التحميل والفراغ والخطأ والنجاح مكتملة.
- اختبارات منطقية وتكاملية مناسبة.
- لا يوجد تكرار لمنطق أعمال الخادم.
