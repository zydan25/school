# وثيقة العمل التنفيذية لمنصة School
الإصدار: 1.0 — التاريخ: 30 أكتوبر 2026 — الحالة: مرجع عمل ملزم

## 1. الغرض
تحول هذه الوثيقة المواصفات الهندسية إلى طريقة تنفيذ قابلة للقياس. كل وحدة تنفذ كتطبيق Django مستقل داخل Modular Monolith. لا تنتقل المهمة إلى المرحلة التالية لمجرد ظهور صفحة أو نموذج؛ بل بعد اكتمال البيانات والخدمات والصلاحيات والواجهات والاختبارات والتوثيق.

## 2. قواعد العمل الملزمة
1. أي تغيير في الكود يرفع إلى GitHub مباشرة بعد حفظه وفحصه؛ لا تتراكم تعديلات محلية غير مرفوعة.
2. لا تعديل مباشر على main في المهام الكبيرة دون توجيه صريح؛ تستخدم فروع واضحة للمراجعة عند الحاجة.
3. كل وحدة لها نماذجها وخدماتها وواجهاتها واختباراتها وملف توثيقها.
4. لا يكتب تطبيق في جداول تطبيق آخر مباشرة؛ التكامل عبر خدمات معلنة وأحداث موثقة.
5. لا يعتمد أي طلب مدرسي على school_id مرسل من العميل وحده؛ سياق المدرسة يثبت بعضوية نشطة وتفويض صالح.
6. لا توجد صلاحية عامة تسمح بكل شيء لمجرد المسمى الوظيفي؛ الصلاحيات تقسم بحسب العملية والبيانات والنطاق.
7. لا يحذف سجل مالي أو أكاديمي معتمد؛ التصحيح يكون بعكس أو تسوية أو إصدار لاحق يحفظ التاريخ.
8. لا تضاف مفاتيح API أو كلمات مرور أو بيانات حقيقية إلى Git.
9. كل ميزة جديدة تتضمن تحديث التوثيق والاختبار وسجل التغييرات.
10. كل دفعة عمل تنتهي بملخص للملفات والسلوك والاختبارات والقيود ورقم الالتزام والرابط.

## 3. تعريف اكتمال المهمة
تعد المهمة مكتملة عند تحقق ما ينطبق من التالي:
- نماذج بعناوين عربية وعلاقات صحيحة وقيود قاعدة بيانات وفهارس.
- migrations مولدة ومراجعة ومضافة إلى Git.
- خدمات الأعمال تستخدم معاملات قاعدة البيانات وتمنع التكرار عند الحاجة.
- استعلامات القراءة لا تتجاوز نطاق المدرسة والفرع.
- API موثق بإصدار وصلاحيات وأخطاء مفهومة.
- واجهة عربية RTL متجاوبة للحاسوب والهاتف.
- بحث وفلاتر وفرز وترقيم وحالات فراغ وتحميل وخطأ.
- سجل تدقيق للعمليات الحساسة.
- اختبارات إيجابية وسلبية، خصوصاً الوصول المتبادل بين المدارس.
- تحديث الوثائق وREADME وCHANGELOG.
- مراجعة التغييرات وعدم إضافة ملفات مؤقتة أو أسرار.
- رفع التغيير والتحقق من وجوده في GitHub.

## 4. البنية المعتمدة
- config: إعدادات المشروع والتوجيه وWSGI/ASGI.
- apps/core: الأساس المشترك وأدوات Django Admin.
- apps/tenants: المدارس والفروع وسياق المدرسة وعزل المستأجر.
- apps/accounts: الهوية والحسابات والعضويات والأدوار والدعوات.
- apps/platform: إدارة المنصة والباقات والاشتراكات.
- apps/academics: السنوات والمراحل والصفوف والشعب والمواد.
- apps/notifications: قوالب الإشعارات والتفضيلات وOutbox.
- apps/auditlog: سجل التدقيق.
- apps/api: واجهات API المشتركة وإصداراتها.
- تطبيقات مستقبلية مستقلة: students, guardians, staff, timetable, attendance, assignments, assessments, results, student_fees, accounting, payroll, procurement, inventory, assets, library, transport, communication, reports, documents, integrations.
- templates وstatic: تخصيص الواجهة العربية.
- tests: اختبارات المجال والتكامل والعزل.
- docs: المواصفات وقرارات التصميم والتشغيل والتقدم.

لا تنشأ تطبيقات مستقبلية كملفات فارغة لمجرد حجز الاسم؛ تنشأ عند بدء نطاقها مع توثيق عقده.

## 5. مراحل العمل ومعايير قبولها

### المرحلة 0 — ضبط المستودع والبيئة
تثبيت إصدار Python وDjango والتبعيات المتوافقة، ضبط متغيرات البيئة، PostgreSQL وRedis، إعداد CI، Docker اختياري، gitignore وملف env.example دون أسرار، وتوحيد طريقة التشغيل والاختبار والرفع.
معيار القبول: مطور جديد يستطيع تجهيز البيئة وتشغيل فحص Django والاختبارات من دليل واضح.

### المرحلة 1 — نواة المنصة والمدارس والهوية والصلاحيات
مستخدم مخصص برقم الهاتف؛ عضويات متعددة؛ فصل الصلاحيات المركزية عن المدرسية؛ أدوار مدرسية ومركزية؛ دعوات آمنة برمز عشوائي لا يحفظ إلا كبصمة؛ سجل المدرسة والكود والحالات؛ الفروع والنطاقات والإعدادات والهوية؛ تهيئة المدرسة في معاملة ذرية؛ سياق مدرسة آمن؛ لوحتان منفصلتان؛ باقات وميزات واشتراكات وفواتير اشتراك المنصة؛ إشعارات وOutbox وسجل تدقيق؛ API للصحة والهوية والمدارس المتاحة وتبديل السياق.
معيار القبول: مدرستان ومستخدمون متنوعون؛ لا يستطيع مستخدم الوصول إلى بيانات المدرسة الأخرى باستخدام معرف مباشر أو Header مزور.

### المرحلة 2 — الإعداد المدرسي والهيكل الأكاديمي
الفروع والمباني والقاعات والمرافق؛ السنوات والفصول والتقويم والعطل؛ المراحل والصفوف والشعب والسعات؛ المواد وتصنيفاتها والمناهج؛ أيام الدوام وفترات الحصص؛ إعدادات مستقلة لكل مدرسة وفرع.
معيار القبول: إعداد مدرستين بخطط أكاديمية مختلفة دون مشاركة سجل بينهما.

### المرحلة 3 — القبول والطلاب وأولياء الأمور
طلبات التقديم وقوائم الانتظار والوثائق؛ ملف طالب وسجل زمني؛ تسجيل سنوي ونقل وترفيع وتخرج وانسحاب؛ علاقات ولي الأمر بالطالب ونوع الولاية وحدود الوصول؛ ربط ولي أمر بعدة أبناء وربط عدة أولياء عند الضرورة؛ استيراد مع معاينة وتقرير أخطاء.
معيار القبول: تسجيل طالب وربطه بولي أمر ثم الوصول إلى بياناته المصرح بها فقط.

### المرحلة 4 — الكادر والموارد البشرية
ملفات الموظفين والمعلمين والمؤهلات والتخصصات والعقود؛ تعيين المعلم للمواد والصفوف والشعب والفروع؛ الحضور الوظيفي والإجازات والسلف والبدلات؛ ملفات العقود وتواريخ الانتهاء.
معيار القبول: المعلم يرى ملفه وإسناداته والبيانات التعليمية اللازمة فقط.

### المرحلة 5 — الجدول المدرسي والحصص
قوالب جدول لكل سنة وفرع؛ أيام العمل والفترات والاستراحات؛ توزيع المواد على الصفوف والشعب؛ إسناد المعلمين والقاعات؛ منع تعارض المعلم والشعبة والقاعـة؛ التحقق من النصاب والحد الأسبوعي؛ جداول بديلة ورمضانية وامتحانية؛ مسودات واعتماد ونشر ونسخ تاريخية؛ تغييرات طارئة وتبديل حصة وتكليف بديل مع سجل.
معيار القبول: رفض كل تعارض وبيان سببه وحفظ نسخ الجداول المنشورة.

### المرحلة 6 — التدريس والحضور والواجبات
سجل الحصة وموضوع الدرس والموارد؛ الحضور اليومي وحضور الحصة والتأخير والغياب والعذر؛ طلبات تصحيح الحضور والموافقات؛ واجبات فردية وجماعية ومرفقات ومواعيد ومحاولات تسليم؛ ملاحظات المعلم وروبرك التقييم والدرجة؛ إشعارات للطالب وولي الأمر.
معيار القبول: المعلم يدير حصصه فقط، والطالب يسلم الواجب، وولي الأمر يراه حسب السياسة.

### المرحلة 7 — الاختبارات والدرجات والنتائج
أنواع الاختبارات والفترات والأوزان؛ جداول ولجان وقاعات ومراقبون؛ بنوك أسئلة ونماذج عند الحاجة؛ رصد الدرجات ومراجعتها واعتمادها ونشرها؛ النجاح والتقريب والرسوب والإعادة والغياب؛ سجل تعديل بعد النشر وسبب وموافقة؛ الشهادات وكشوف الدرجات والترتيب.
معيار القبول: لا تنشر نتيجة قبل اعتمادها وتبقى التعديلات التاريخية قابلة للتدقيق.

### المرحلة 8 — رسوم الطلاب والتحصيل
هياكل رسوم حسب السنة والصف والفرع والفئة؛ التسجيل والدراسة والكتب والنقل والأنشطة؛ فواتير وأقساط؛ منح وخصومات وإعفاءات بموافقات وحدود؛ قبض نقدي وبنكي وتحويل؛ تخصيص الدفعات على الاستحقاقات؛ أرصدة دائنة واسترداد وعكس وكشوف حساب.
معيار القبول: رصيد الطالب يطابق الاستحقاقات والمدفوعات والتسويات مع سند وإيصال.

### المرحلة 9 — محاسبة مستقلة لكل مدرسة
دفتر ودليل حسابات مستقل؛ فترات مالية ومراكز تكلفة؛ قيود مزدوجة لا تحذف بعد الترحيل؛ صناديق وبنوك وتحويلات وتسويات؛ عملاء وموردون وذمم؛ الأستاذ العام والمساعد وميزان المراجعة؛ قائمة الدخل والمركز المالي والتدفقات النقدية؛ الأصول والإهلاك والميزانية؛ تكامل الرسوم والرواتب والمشتريات والمخزون بمراجع فريدة؛ الإقفال والافتتاح.
معيار القبول: القيد متوازن، الحسابات من المدرسة نفسها، يمنع الترحيل في فترة مغلقة والتكرار، وتتطابق التقارير مع الأستاذ.

### المرحلة 10 — الرواتب والمشتريات والمخزون والأصول
مسيرات الرواتب والاستحقاقات والسلف والخصومات؛ اعتماد وصرف وقسائم؛ الموردون والعروض وأوامر الشراء والاستلام؛ المستودعات والأصناف والوحدات والحركات والجرد؛ الأصول والإهلاك والنقل والاستبعاد.
معيار القبول: لكل حركة أثر تدقيقي وأثر مالي صحيح.

### المرحلة 11 — الوحدات الخدمية الاختيارية
المكتبة والإعارة والغرامات؛ النقل والحافلات والسائقون والمسارات والصيانة؛ العيادة مع قيود بيانات حساسة؛ الأنشطة والرحلات والموافقات؛ المقصف والمبيعات والمخزون عند تفعيل الوحدة.
معيار القبول: تفعيل الوحدة أو تعطيلها وفق الباقة دون التأثير على الوحدات الأخرى.

### المرحلة 12 — التواصل والتطبيق الموحد
مركز إشعارات داخل النظام وPush وبريد وSMS وWhatsApp؛ قوالب مخصصة لكل مدرسة وحدث؛ التفضيلات ومحاولات التسليم؛ محادثات بين مستخدمين مخولين؛ Flutter موحد لاكتشاف المدرسة وتسجيل الدخول واختيار المؤسسة وواجهة حسب الدور والأبناء؛ إدارة جلسات ومزامنة آمنة.
معيار القبول: لا يصل إشعار أو رسالة عن سجل لا يحق للمستلم الوصول إليه.

### المرحلة 13 — التقارير والإطلاق
تقارير أكاديمية ومالية وإدارية؛ PDF/Excel مع سجل طلبات؛ اختبارات تحميل وأمان وعزل واستعادة نسخ؛ مدرسة تجريبية وبيانات اصطناعية؛ تدريب ودليل مستخدم وخطة تراجع ومراقبة.
معيار القبول: نجاح رحلة تشغيل من القبول حتى النتائج والتحصيل والإقفال مع سجل تدقيق.

## 6. آلية تنفيذ كل وحدة
1. تحليل السيناريوهات والاستثناءات.
2. تحديد المسؤولية والملكية والعلاقات.
3. تسجيل القرار المعماري عند الحاجة.
4. إنشاء models/services/selectors/admin/api.
5. توليد migrations ومراجعتها.
6. إنشاء واجهات عربية RTL واضحة في Django Admin ثم الواجهات التشغيلية.
7. كتابة اختبارات المجال والتكامل والعزل.
8. مراجعة الأمان والأداء.
9. تحديث الوثائق وسجل التقدم.
10. تشغيل الفحوص ومراجعة التغييرات.
11. commit وpush وذكر SHA والرابط.
12. الانتقال إلى المهمة التالية.

## 7. معايير لوحة الإدارة العربية
- RTL على جميع الصفحات.
- استخدام Django Unfold لتخصيص التنقل والبطاقات والمؤشرات والقوالب.
- ألوان عالية التباين وهوية واضحة وخط عربي ومساحات مريحة.
- بحث ومرشحات حسب المدرسة والفرع والحالة والسنة.
- إجراءات جماعية بتأكيد وسجل.
- تفاصيل السجل تعرض العلاقات والنشاط.
- الأرشفة بدلاً من الحذف في السجلات التاريخية والمالية.
- لوحة المنصة تفصل الاشتراكات عن دفاتر المدارس.
- لوحة المدرسة لا تعرض إلا نطاق المدرسة النشطة، والتحقق يتم في الخادم عند كل طلب.

## 8. سياسة الرفع
كل دفعة تستخدم رسالة واضحة من نوع feat أو fix أو docs. لا تضم ملفات البيئة الحقيقية أو قواعد بيانات محلية أو cache. ترفع مباشرة إلى الفرع المتفق عليه بعد الفحص. يسجل رابط الالتزام ونتيجة CI. إذا تعذر الاختبار بسبب غياب اعتماديات أو قاعدة بيانات، يذكر ذلك صراحة ولا يدعى نجاحه.

## 9. سجل تقدم المشروع
تسجل حالة كل عنصر: غير مبدوء، قيد التنفيذ، منفذ محلياً، مرفوع إلى GitHub، اختبارات ناجحة، معتمد. لا تعد المرحلة مكتملة إلا عند تحقق معايير قبولها.
